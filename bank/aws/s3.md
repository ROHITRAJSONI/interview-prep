# AWS S3

## Q: How do you securely let a client upload a large file directly to S3?
### Solution
The backend authenticates the user and returns a **pre-signed URL** (or a pre-signed POST with conditions such as content-length range and content-type) with a short expiry. The client uploads straight to S3, so the bytes never pass through your service. For files over ~100 MB use **multipart upload** with a pre-signed URL per part. Multipart parallelizes the upload and lets it resume.

Then an S3 event (→ EventBridge/SQS) triggers processing (virus scan, validation). Lock down the bucket: Block Public Access, SSE-KMS encryption, a bucket policy that denies non-TLS access, and a lifecycle rule to abort incomplete multipart uploads.

## Q: What consistency does S3 provide, and how do you design for high request rates?
### Solution
Since Dec 2020 S3 has **strong read-after-write consistency** for PUTs, DELETEs and LISTs. There's no more eventual-consistency window.

Throughput: at least **3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per prefix**, and S3 scales by partitioning prefixes automatically. Spread hot keys across prefixes (e.g. `/date/hash/…`), use byte-range GETs for parallel downloads, CloudFront for read-heavy public content, and Transfer Acceleration for long-distance uploads. On a sudden spike S3 may return 503 SlowDown. The SDK retries with backoff.
