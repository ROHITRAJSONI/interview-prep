## Q1 (coding): Implement a promise pool with a concurrency limit

Implement `promisePool(tasks, limit)` where `tasks` is an array of functions returning promises (e.g. calls to a payments API). Run them with at most `limit` in flight at once.

Constraints:
- Results returned in input order, regardless of completion order.
- Reject on first failure and stop starting new tasks (fail-fast).
- Synchronous throws in a task must become rejections; invalid `limit` rejects; empty input resolves `[]`.
- No libraries.

Example: 5 tasks with `limit = 2` -> resolves `['a','b','c','d','e']`, never more than 2 running simultaneously.

<details><summary>Solution</summary>

Approach: start `min(limit, n)` workers; each time a task settles successfully, launch the next one (refilling the freed slot). Store each result at its index to preserve order. A `failed` flag stops new launches after a rejection.

```javascript
function promisePool(tasks, limit) {
  if (!Number.isInteger(limit) || limit < 1) {
    return Promise.reject(new RangeError('limit must be a positive integer'));
  }
  return new Promise((resolve, reject) => {
    const results = new Array(tasks.length);
    let next = 0;
    let done = 0;
    let failed = false;
    if (tasks.length === 0) return resolve(results);

    const launch = () => {
      if (failed || next >= tasks.length) return;
      const i = next++;
      Promise.resolve()
        .then(() => tasks[i]())          // sync throws become rejections
        .then(value => {
          results[i] = value;
          if (++done === tasks.length) resolve(results);
          else launch();                 // refill the freed slot
        }, err => {
          failed = true;
          reject(err);
        });
    };
    for (let k = 0; k < Math.min(limit, tasks.length); k++) launch();
  });
}
```

**Complexity:** O(n) time overhead, O(n) space for results; wall-clock ≈ total work / limit.

**Follow-ups / pitfalls:**
- Why not `Promise.all(tasks.map(t => t()))`? It starts everything at once and can overwhelm the downstream service or hit rate limits. Tasks must be *factories*, not already-started promises.
- Fail-fast does not cancel in-flight tasks; use `AbortController` for real cancellation.
- Variant: collect per-task `{status, value|reason}` like `allSettled` instead of fail-fast.
- Add retry with exponential backoff and jitter for 429/503, and honour idempotency keys for payment calls.
- The `Promise.resolve().then(...)` wrapper is what turns sync throws into rejections.

## Q2: How does `this` get determined in JavaScript, and what bugs does it cause in callbacks and class methods?

<details><summary>Solution</summary>

**Answer:** `this` is decided by *how a function is called*, not where it's defined — except arrow functions, which capture `this` lexically from the enclosing scope.

Rules, in precedence order:
1. `new Fn()` — `this` is the new object.
2. `fn.call/apply/bind(obj)` — explicitly `obj` (bind is permanent).
3. `obj.method()` — `this` is `obj`.
4. Plain call `fn()` — `undefined` in strict mode/modules/classes, global object in sloppy mode.

**Classic bug:** detaching a method loses the receiver.
```javascript
class Account {
  balance = 100;
  withdraw(n) { this.balance -= n; }
}
const a = new Account();
setTimeout(a.withdraw, 0, 10);         // TypeError: this is undefined
setTimeout(() => a.withdraw(10), 0);   // OK
setTimeout(a.withdraw.bind(a), 0, 10); // OK
```
Same issue with event handlers, `array.map(obj.method)`, and React-style callbacks.

**Fixes and trade-offs:**
- Wrap in an arrow at the call site (simple, allocates a closure per call).
- `bind` in the constructor, or define the method as a class-field arrow (`withdraw = n => {...}`): `this` is always correct, but each instance gets its own function copy rather than a shared prototype method, which costs memory and makes stubbing in tests harder.
- Don't use arrows as object-literal methods or prototype methods when you need dynamic `this`; arrows also have no `arguments` and can't be constructors.

**Pitfalls to mention:** DOM handlers set `this` to the element for regular functions; a bound function can't be rebound by a later `call`; passing methods to APIs that invoke them bare. In an interview, state the four rules, show the detached-method bug, then the fix with its trade-off.

</details>

## Q3: `Promise.all`, `allSettled`, `race`, `any` — when do you use each? How do you handle errors in async/await correctly?

<details><summary>Solution</summary>

**Answer:** Pick based on what a single failure should mean for the whole operation.

- `Promise.all` — all-or-nothing. Rejects immediately on the first rejection (others keep running, results discarded). Use when results depend on each other, e.g. loading account + limits + FX rate to render one screen.
- `Promise.allSettled` — never rejects; gives `{status, value|reason}` per input. Use for independent work where partial success is fine, e.g. sending notifications to many users, batch reconciliation reports.
- `Promise.race` — first to *settle* wins, success or failure. Use for timeouts: `race([fetchData(), timeout(3000)])`.
- `Promise.any` — first to *fulfil*; rejects with `AggregateError` only if all fail. Use for hedged requests to redundant replicas/regions.

**Async/await error handling:**
- `try/catch` around `await` catches rejections; forgetting `await` (or `return` in a `.then` chain) means the error escapes and becomes an `unhandledRejection` — which crashes Node ≥15 by default.
- Sequential `await` in a loop serialises work; for independent calls start them first, then `await Promise.all`. For large fan-out, use a pool (limit concurrency).
- `await` inside `forEach` doesn't wait — use `for...of` or `Promise.all(map(...))`.
- Don't swallow errors: catch, add context, rethrow; use `finally` for cleanup.
- A timeout via `race` doesn't cancel the underlying work — pass an `AbortSignal` to `fetch`.
- Preserve the original error with `new Error('msg', { cause: err })`.

**Fintech angle:** never auto-retry non-idempotent payment calls without an idempotency key, and log correlation IDs on rejection.

</details>
