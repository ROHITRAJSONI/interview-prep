## Q1 (coding): SQS-triggered payment Lambda with idempotency and partial batch failures

Implement the core logic of a Lambda handler that consumes a batch of SQS messages (`messageId`, body `"paymentId,cents"`) and applies payments.

Requirements:
- SQS delivers **at-least-once**, so the same `paymentId` may arrive twice (even within one batch). A payment must be applied **at most once**.
- Return a `batchItemFailures` response containing only the IDs of messages that failed (so successes are not redelivered).
- For a **FIFO** queue, once a message fails, every later message in the batch must also be reported as failed, to preserve ordering.
- If processing fails, the idempotency key must be released so a retry can succeed.
- Model the idempotency table as a conditional put (`attribute_not_exists`), as you would with DynamoDB.

Example: batch `m1:p1,100`, `m2:p1,100` (duplicate), `m3:p3,300` (downstream throws), `m4:p4,400`. Expected: p1 is processed once, response is `[m3, m4]`.

<details><summary>Solution</summary>

**Approach:** The mapping must have `FunctionResponseTypes: ReportBatchItemFailures`. Throwing from the handler would make the whole batch visible again, so the handler catches per message and returns only the failed IDs. Idempotency is a conditional write (`putIfAbsent` here, `PutItem` with `attribute_not_exists(pk)` in DynamoDB). A duplicate is treated as success. On failure the key is released, so the redelivery can run. In production, add a TTL on the key and an `IN_PROGRESS` timeout, so a crash mid-processing doesn't block the key forever.

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.stream.*;

/** Standalone model of an SQS-triggered Lambda handler with partial batch failure + idempotency. */
public class Solution {
    record SqsMessage(String messageId, String body) {}
    record BatchResponse(List<String> batchItemFailures) {}

    /** Stand-in for a DynamoDB table with conditional put (attribute_not_exists). */
    static class IdempotencyStore {
        enum State { IN_PROGRESS, DONE }
        private final ConcurrentHashMap<String, State> map = new ConcurrentHashMap<>();
        /** @return true if this caller acquired the key (first time). */
        boolean tryStart(String key) { return map.putIfAbsent(key, State.IN_PROGRESS) == null; }
        void complete(String key) { map.put(key, State.DONE); }
        void release(String key) { map.remove(key, State.IN_PROGRESS); } // allow retry after failure
    }

    interface PaymentProcessor { void process(String paymentId, long cents); }

    static class Handler {
        private final IdempotencyStore store;
        private final PaymentProcessor processor;
        Handler(IdempotencyStore s, PaymentProcessor p) { store = s; processor = p; }

        BatchResponse handle(List<SqsMessage> batch) {
            List<String> failed = new ArrayList<>();
            boolean poisoned = false; // for FIFO: after first failure, fail the rest to keep ordering
            for (SqsMessage m : batch) {
                if (poisoned) { failed.add(m.messageId()); continue; }
                try {
                    processOne(m);
                } catch (Exception e) {
                    failed.add(m.messageId());
                    poisoned = true; // remove this line for standard queues (independent messages)
                }
            }
            return new BatchResponse(failed);
        }

        private void processOne(SqsMessage m) {
            String[] parts = m.body().split(",");           // "paymentId,cents"
            if (parts.length != 2) throw new IllegalArgumentException("bad payload " + m.messageId());
            String paymentId = parts[0];
            long cents = Long.parseLong(parts[1]);
            if (!store.tryStart(paymentId)) return;         // duplicate delivery -> treat as success
            try {
                processor.process(paymentId, cents);
                store.complete(paymentId);
            } catch (RuntimeException e) {
                store.release(paymentId);
                throw e;
            }
        }
    }

    public static void main(String[] args) {
        Set<String> processed = new LinkedHashSet<>();
        Handler h = new Handler(new IdempotencyStore(), (id, c) -> {
            if (id.equals("p3")) throw new IllegalStateException("downstream down");
            processed.add(id);
        });
        List<SqsMessage> batch = List.of(
            new SqsMessage("m1", "p1,100"), new SqsMessage("m2", "p1,100"),
            new SqsMessage("m3", "p3,300"), new SqsMessage("m4", "p4,400"));
        BatchResponse r = h.handle(batch);
        System.out.println("failed=" + r.batchItemFailures() + " processed=" + processed);
        if (!r.batchItemFailures().equals(List.of("m3", "m4")) || !processed.equals(Set.of("p1")))
            throw new AssertionError();
    }
}
```

**Complexity:** O(n) time for n messages, O(n) space for the failure list. In production each message costs one conditional write plus the downstream call.

**Follow-ups an interviewer will ask:**
- Why not just throw? The whole batch is retried, so successful messages are reprocessed, and the batch can hit `maxReceiveCount` and go to the DLQ because of one bad message.
- A crash between `process` and `complete` leaves `IN_PROGRESS`. Fix it with a lease/expiry on the record and make the downstream call itself idempotent by passing the paymentId as the idempotency key. Powertools for AWS Lambda (Java) has an `@Idempotent` annotation that does this.
- Visibility timeout should be at least 6× the function timeout. Set a DLQ with `maxReceiveCount`, and use `MaximumConcurrency` to protect downstream systems.
- On FIFO queues the "fail the rest" rule keeps per-`MessageGroupId` order. A more precise version only fails the rest of the same group.

</details>

## Q2: Your Lambda talks to an RDS database and starts failing with "too many connections" under traffic spikes. Why, and how do you fix it?

<details><summary>Solution</summary>

**Direct answer:** Each concurrent Lambda execution environment holds its own connection. Concurrency scales with traffic (up to the account limit, with burst scaling), so 500 concurrent invocations means 500 connections, which exceeds what a small RDS instance allows. Unlike a long-lived server, there is no shared pool across environments.

**Fixes, in the order I'd reach for them:**
1. **RDS Proxy.** It multiplexes many Lambda connections onto a small pool of DB connections. It also helps with failover time and lets you use IAM auth with Secrets Manager. Cost: extra latency, a per-vCPU charge, and *pinning* (session state such as `SET` or temp tables pins a connection and cuts the multiplexing benefit).
2. **Cap concurrency.** Reserved concurrency on the function, or `MaximumConcurrency` on the SQS event source mapping, gives a hard ceiling that the DB can handle. Excess work waits in the queue (SQS) or is throttled (sync callers get 429s, so they need retries).
3. **Connection hygiene.** Create the connection outside the handler and reuse it on warm invocations. Use a pool size of 1 per environment. Handle stale connections after a freeze, with validation or reconnect on error. Set a short idle timeout.
4. **Reduce DB dependence.** Use DynamoDB or the RDS Data API for spiky workloads. Put a cache in front of reads.

**Trade-offs and pitfalls:**
- Reserved concurrency also *guarantees* capacity for that function, but it reduces the pool for other functions in the account.
- Don't mistake this for a DB sizing problem only. Raising `max_connections` just burns memory on the DB.
- A Lambda in a VPC needs a route to the DB, and a NAT gateway if it also needs the internet.
- Monitor `DatabaseConnections`, `ConcurrentExecutions` and `Throttles` in CloudWatch.

</details>

## Q3: A Lambda invoked asynchronously (for example from S3 or EventBridge) fails. What happens, and how do you build reliable failure handling for a banking workflow?

<details><summary>Solution</summary>

**Direct answer:** Async invocations go into an internal Lambda queue. On error, Lambda **retries twice by default** (configurable 0–2) with delays of about 1 minute and then 2 minutes. Events are kept up to **6 hours** (configurable, max). After that the event is dropped unless you configured a **DLQ** (SQS or SNS) or, preferably, an **on-failure destination**. Both sides see at-least-once delivery, so the function can run more than once for the same event.

**How I'd design it for a bank:**
- **Idempotency is mandatory.** Retries and duplicate event delivery are normal. Use a conditional write keyed on the business ID (or the event ID), not the request ID, because retries get a new invocation but carry the same event.
- **Destinations over DLQ.** An on-failure destination (SQS, SNS, EventBridge or Lambda) receives the failed event plus error context, such as the request ID, retry count and stack trace. A plain DLQ only gets the event payload. Alarm on destination queue depth, and have a redrive runbook.
- **Tune retries.** For non-idempotent or very expensive work, set retries to 0 and handle retries explicitly. Set `MaximumEventAge` so stale events (for example a price quote) are discarded rather than run hours later.
- **Distinguish failure types.** Throw for transient errors, which the retry will fix. For poison or validation errors, do not throw. Route them straight to a quarantine queue, since retrying will never succeed.
- **Ordering is not guaranteed** in async invocations. If ordering matters, use SQS FIFO or Kinesis as the source instead.
- **Timeouts:** an invocation that times out counts as a failure and retries, so the function must be safe to restart halfway through. Pair this with a saga or Step Functions when the workflow has several steps that need compensation.

</details>
