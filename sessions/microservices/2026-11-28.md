## Q1 (coding): Build an idempotent payment endpoint (Idempotency-Key)

Mobile clients retry `POST /payments` on timeouts, and the load balancer may also retry. Implement `IdempotencyService.execute(key, requestBody, action)` so that:

- The same `Idempotency-Key` with the same payload runs `action` **exactly once**; all callers get the same response.
- Concurrent duplicates while the first is still running wait for it (or get `409` after a timeout).
- The same key with a *different* payload returns `422`.
- Keys expire after a TTL (24h); `5xx`/exceptions are not cached so the client can retry.

Example: 8 threads call `execute("k1", "{amt:10}", charge)` concurrently -> all 8 receive `201 charge-1`, charge executed once. A later call with `{amt:99}` -> `422`.

<details><summary>Solution</summary>

Approach: atomically *claim* the key with `ConcurrentHashMap.compute`, storing a request fingerprint plus a `CompletableFuture` for the outcome. The winner runs the action and completes the future; losers block on the future. In production the map is a DB table with a unique constraint on the key (or Redis `SET NX`), and the business write and key record commit in the same transaction.

```java
import java.time.Duration;
import java.util.Objects;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.function.Supplier;

/** Idempotent payment endpoint logic: same Idempotency-Key => same result, executed once. */
public class Solution {

    record Response(int status, String body) {}

    /** Stored state of a key: fingerprint of request + a future of the outcome. */
    private record Entry(String fingerprint, CompletableFuture<Response> result, long createdNanos) {}

    static class IdempotencyService {
        private final ConcurrentHashMap<String, Entry> store = new ConcurrentHashMap<>();
        private final long ttlNanos;

        IdempotencyService(Duration ttl) { this.ttlNanos = ttl.toNanos(); }

        Response execute(String key, String requestBody, Supplier<Response> action) {
            String fp = Integer.toHexString(Objects.hash(requestBody)); // use SHA-256 in prod
            long now = System.nanoTime();
            Entry mine = new Entry(fp, new CompletableFuture<>(), now);

            // atomic claim; also evicts an expired entry
            Entry existing = store.compute(key, (k, cur) ->
                    (cur == null || now - cur.createdNanos > ttlNanos) ? mine : cur);

            if (existing != mine) {
                if (!existing.fingerprint().equals(fp)) {
                    return new Response(422, "Idempotency-Key reused with different payload");
                }
                try {                       // concurrent duplicate waits for the first call
                    return existing.result().get(5, TimeUnit.SECONDS);
                } catch (TimeoutException e) {
                    return new Response(409, "Original request still in progress");
                } catch (InterruptedException | ExecutionException e) {
                    Thread.currentThread().interrupt();
                    return new Response(500, "Failed waiting for original");
                }
            }
            try {
                Response r = action.get();
                mine.result().complete(r);
                if (r.status() >= 500) store.remove(key, mine); // don't cache transient failures
                return r;
            } catch (RuntimeException ex) {
                store.remove(key, mine);     // allow retry
                mine.result().complete(new Response(500, "error"));
                throw ex;
            }
        }
    }

    public static void main(String[] args) throws Exception {
        IdempotencyService svc = new IdempotencyService(Duration.ofHours(24));
        AtomicInteger charges = new AtomicInteger();
        Supplier<Response> charge = () -> {
            try { Thread.sleep(100); } catch (InterruptedException ignored) {}
            return new Response(201, "charge-" + charges.incrementAndGet());
        };
        ExecutorService pool = Executors.newFixedThreadPool(8);
        var futures = new java.util.ArrayList<Future<Response>>();
        for (int i = 0; i < 8; i++) futures.add(pool.submit(() -> svc.execute("k1", "{amt:10}", charge)));
        for (var f : futures) System.out.println(f.get());
        System.out.println("charges executed = " + charges.get());       // 1
        System.out.println(svc.execute("k1", "{amt:99}", charge));        // 422
        pool.shutdown();
    }
}
```

Verified: compiled with javac 21 and run; output shows one charge for 8 concurrent calls and a 422 for the mismatched payload.

**Complexity:** O(1) per call, O(K) memory for K live keys (needs a sweeper for expired entries).

**Pitfalls / follow-ups:**
- Check-then-put (`get` then `put`) is a race; the claim must be atomic.
- Fingerprint must be a cryptographic hash (SHA-256) of a canonical payload; `Objects.hash` is demo-only.
- Multi-instance deployment: in-memory map is useless; use a shared store with a unique key, and a state column (IN_PROGRESS/COMPLETED) with a lock timeout for crashed owners.
- Crash between charging the provider and recording the result: pass the same idempotency key downstream to the PSP.
- Scope keys per client/tenant, and keep responses (status + body) so replays are byte-identical.

</details>

## Q2: How do you deploy a breaking change to a service's API or database schema with zero downtime when many consumers depend on it?

<details><summary>Solution</summary>

**Answer:** Never ship a breaking change in one step. Use backward-compatible, additive changes and the expand/contract (parallel change) pattern, so old and new versions can run side by side during a rolling deploy.

**Reasoning:** During a rolling or canary release, v1 and v2 of the service run simultaneously, and consumers upgrade on their own schedule. So every release must be compatible with the previous one.

**API:** 
- Be tolerant: add optional fields, never remove or repurpose existing ones; consumers ignore unknown fields (tolerant reader).
- For genuinely breaking changes, version (`/v2` or media type), run both, track v1 usage via metrics/logs, announce deprecation with `Sunset` headers, and remove only when traffic is zero.
- Use consumer-driven contract tests (Pact) in CI so the provider build fails if it breaks a real consumer.

**Database (rename column `name` -> `full_name`):**
1. Expand: add `full_name` (nullable). Deploy code that writes both and reads old with fallback.
2. Backfill in batches (throttled, to avoid replication lag/locks).
3. Switch reads to the new column.
4. Contract: stop writing the old column, then drop it in a later release.

Never combine a destructive migration with the code release that needs it; migrations run separately and ahead of the code (Flyway/Liquibase), and every step must be rollback-safe.

**Events:** Use a schema registry with BACKWARD/FULL compatibility; add fields with defaults.

**Trade-offs:** More releases and temporary dual-write complexity versus no downtime and an always-available rollback. 

**Pitfalls:** dropping a column while an old pod still runs; `NOT NULL` additions without defaults locking big tables; forgetting batch jobs or reporting consumers that read the DB directly.

</details>

## Q3: A user-facing request spanning ~12 services is intermittently slow (p99 spikes). How do you find the cause?

<details><summary>Solution</summary>

**Answer:** Start with distributed tracing to find *which hop* is slow, correlate with metrics and logs for *why*, then fix and add an SLO alert.

**Steps:**
1. **Scope it with metrics (RED):** rate, errors, duration per service from Prometheus/CloudWatch. Is it one endpoint, one region, one customer segment, or started after a deploy?
2. **Trace:** with OpenTelemetry, a trace ID is created at the edge and propagated through W3C `traceparent` headers (and Kafka message headers). Pull slow traces from Jaeger/Tempo/X-Ray and read the waterfall: which span dominates? Is it serial calls that could be parallel, an N+1 call pattern, a retry storm, or time spent waiting in a queue?
3. **Correlate logs:** put the trace ID in every log line (MDC in Spring) so one search reveals the detail behind the slow span.
4. **Find root cause by category:** a slow DB query or missing index, connection-pool or thread-pool exhaustion (look at pool wait time), GC pauses, a noisy neighbour, cold starts, a downstream with no timeout, retries amplifying load, or a cache stampede after expiry.
5. **Fix and protect:** timeouts shorter than the caller's deadline, circuit breakers and bulkheads, bounded retries with jitter, caching, parallelising independent calls.

**Trade-offs:** Tracing every request is expensive. Use head sampling (1-5%) plus tail-based sampling that always keeps slow or errored traces, which is what catches p99 outliers. Averages hide the problem; always look at percentiles and exemplars.

**Pitfall:** Broken context propagation through async executors, message queues or a non-instrumented service leaves gaps in the trace. Standardize on a shared library/agent.

</details>
