## Q1 (coding): First overdraft per account using window functions

A bank stores a ledger in `transactions(txn_id PK, account_id, amount DECIMAL(12,2), txn_ts TIMESTAMP)`. `amount` is positive for credits and negative for debits. Write a single MySQL 8.0 query that returns, for every account that was ever overdrawn (running balance < 0): the first transaction that pushed it negative, the timestamp, the balance after it, and how many transactions in total left the account overdrawn.

Constraints: no stored procedures or variables (`@running := ...` is deprecated); several transactions can share the same `txn_ts`, so ordering must be deterministic (break ties with `txn_id`); the table has ~200M rows, so say which index you'd add.

Example (sample data is in `solution.sql`): account 100 has balances 500, 300, -100, 200, -100, and account 300 has -10, 0. Expected output:

| account_id | first_overdraft_txn | first_overdraft_ts | balance_after | overdrawn_txn_count |
|---|---|---|---|---|
| 100 | 3 | 2026-01-03 11:00:00 | -100 | 2 |
| 300 | 8 | 2026-01-01 08:00:00 | -10 | 1 |

<details><summary>Solution</summary>

Approach: compute the running balance with `SUM() OVER (PARTITION BY account_id ORDER BY txn_ts, txn_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`. Then number the negative rows per account and keep `rn = 1`. Count the negative rows with a correlated subquery over the CTE. (Alternative: a second window `COUNT(*) OVER (PARTITION BY account_id)` on the flagged rows, which avoids the subquery.)

```sql
WITH running AS (
  SELECT account_id, txn_id, txn_ts, amount,
         SUM(amount) OVER (PARTITION BY account_id
                           ORDER BY txn_ts, txn_id
                           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS balance
  FROM transactions
),
flagged AS (
  SELECT r.*,
         ROW_NUMBER() OVER (PARTITION BY account_id ORDER BY txn_ts, txn_id) AS rn
  FROM running r
  WHERE balance < 0
)
SELECT f.account_id, f.txn_id AS first_overdraft_txn, f.txn_ts AS first_overdraft_ts,
       f.balance AS balance_after,
       (SELECT COUNT(*) FROM running x
         WHERE x.account_id = f.account_id AND x.balance < 0) AS overdrawn_txn_count
FROM flagged f
WHERE f.rn = 1
ORDER BY f.account_id;
```

The full schema, sample data and query are in `sessions/mysql/2026-11-26/solution.sql`. I ran it on SQLite 3.x, which supports the same window syntax, and it returned the expected rows above.

**Complexity:** one pass over the data, sorted per partition: O(n log n) overall, or O(n) if the index below supplies the order. Memory is roughly O(largest partition), because the window buffers a partition.

**Index:** `(account_id, txn_ts, txn_id)` matches the `PARTITION BY` / `ORDER BY`, so MySQL can skip the filesort (check `EXPLAIN` for the absence of `Using filesort`).

**Pitfalls / follow-ups**
- Without an explicit `ROWS` frame, the default frame is `RANGE ... CURRENT ROW`, which treats rows with equal `ORDER BY` values as peers. Tied timestamps would then get the same balance, so always add the `txn_id` tiebreaker and `ROWS`.
- Use `DECIMAL`, never `FLOAT`, for money.
- A window function can't appear in `WHERE`, which is why we need the CTE layers.
- On 200M rows you would not recompute this on demand. Keep a `balance_after` column or a balance table updated in the same transaction, and use the query for audits and backfills.
- Follow-up: "find accounts overdrawn for 3 or more consecutive days" is the gaps-and-islands pattern (`date - ROW_NUMBER()` grouping).

## Q2: How do you make a funds transfer between two accounts safe in MySQL/InnoDB under concurrency (no lost updates, no double debits, no deadlock storms)?

<details><summary>Solution</summary>

**Short answer:** do it in one transaction, lock both rows in a consistent order with `SELECT ... FOR UPDATE`, enforce the invariant in SQL, make the request idempotent, and retry on deadlock.

**Reasoning**
1. **Locking.** Under REPEATABLE READ a plain `SELECT balance` followed by `UPDATE` is a read-modify-write race, so two concurrent debits can both pass the check. Use `SELECT ... FROM account WHERE id IN (:a,:b) ORDER BY id FOR UPDATE`. Locking in ascending id order means A→B and B→A transfers can't deadlock against each other.
2. **Enforce the invariant in the statement.** `UPDATE account SET balance = balance - :amt WHERE id=:a AND balance >= :amt`, then check `affected rows = 1`. This works even without the explicit lock, and it's the optimistic alternative (a `version` column plus compare-and-set), which is better when contention is low.
3. **Idempotency.** Clients and gateways retry. Insert a row into a `transfer` table with a `UNIQUE (idempotency_key)` in the same transaction. A duplicate key means the transfer already happened, so return the original result instead of debiting twice.
4. **Double-entry ledger.** Insert immutable debit and credit rows rather than only mutating balances, so you can audit and reconcile.
5. **Deadlocks are normal.** InnoDB kills one victim with error 1213, so wrap the transaction in a bounded retry with jitter. Keep transactions short, with no network calls inside (calling a fraud service while holding row locks is a classic outage).

**Trade-offs / pitfalls**
- Pessimistic locks are simple and correct for hot accounts, but they serialize. A very hot account, like a merchant settlement account, needs sharded sub-balances or an async ledger.
- Gap locks from range predicates under REPEATABLE READ can widen contention, so lock by primary key.
- Autocommit on means each statement commits alone, which silently breaks atomicity.
- Across two databases or services you can't use a local transaction. Use a saga or outbox pattern with idempotent steps.

```sql
START TRANSACTION;
INSERT INTO transfer(idempotency_key, from_id, to_id, amount) VALUES (?,?,?,?);
SELECT id, balance FROM account WHERE id IN (?,?) ORDER BY id FOR UPDATE;
UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?;
UPDATE account SET balance = balance + ? WHERE id = ?;
COMMIT;
```

## Q3: You must add a column and an index to a 500M-row production MySQL table with zero downtime. How do you do it, and how do replicas factor in?

<details><summary>Solution</summary>

**Short answer:** use an online DDL method (InnoDB `ALGORITHM=INPLACE/INSTANT` where the operation supports it, otherwise a shadow-table tool such as gh-ost or pt-online-schema-change). Rehearse it on a production-sized copy, and watch replication lag and metadata locks throughout.

**Reasoning**
- **MySQL 8.0 `ALGORITHM=INSTANT`:** adding a nullable column (or one with a default) only changes metadata, so it finishes in milliseconds with no rebuild. Always specify `ALGORITHM=INSTANT, LOCK=NONE` explicitly so MySQL errors out instead of silently falling back to a table copy.
- **Adding a secondary index** is `INPLACE, LOCK=NONE`. Reads and writes continue, but it still scans 500M rows, consumes I/O and buffer pool, and writes made meanwhile are buffered in the online-alter log. It can also fail late if that log fills up.
- **Unsupported changes** (changing a column type, changing the primary key) need a full rebuild. gh-ost creates a shadow table, copies rows in chunks, tails the binlog to apply ongoing changes, then does an atomic cut-over. It is throttleable and can be paused, unlike triggers, which is why many teams prefer it to pt-osc.
- **Replicas:** a DDL replays on each replica as a single long statement, so replicas can lag by as long as the build took, and anything reading from replicas sees stale data. Throttle on replica lag and run during low traffic. With managed services, a blue/green deployment is an alternative.
- **Metadata lock trap:** the ALTER needs a brief exclusive MDL at the start and end. One long-running transaction or idle open connection blocks it, and then every new query queues behind the ALTER, which causes an outage. Set `lock_wait_timeout` low and check for long transactions first.

**Rollout discipline (expand/contract):** deploy code that tolerates both schemas, add the column, backfill in small batches, switch reads, then drop the old column in a later release. Keep a rollback plan, because DDL isn't transactional in MySQL.

</details>
